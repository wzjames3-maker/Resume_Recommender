# MaxKB 人事模块化改造设计

## 目标

以 MaxKB（`1panel-dev/MaxKB`）为产品内核，构建"知识库构建 + 知识库问答 + 代码级人事工作流"的招聘知识平台。人事业务作为 MaxKB 内的定制 Django 模块存在，不重复实现知识库与问答能力。

## 产品形态

```text
MaxKB 主仓库（fork v2，GPL-3.0）
├── 保留：知识库构建、RAG 问答、引用溯源、会话管理
├── 保留：模型配置（LLM / Embedding / Rerank）、文档解析
├── 保留：用户 / 工作区 / 角色权限
├── 隐藏：可视化工作流编排、MCP、函数库、应用市场、应用发布
└── 新增：人事模块 apps/hr
    ├── 简历解析与结构化
    ├── 候选人 / 职位管理
    ├── 智能搜人（意图路由 + RAG 检索）
    ├── 面试管理（结果状态机）
    └── Offer 管理（Offer / 入职 / 拒绝）
```

## 关键原则

1. **MaxKB 是平台内核**：知识库、问答、权限、模型接入全部复用，不重做。
2. **人事是定制业务模块**：只实现 MaxKB 没有的招聘领域能力。
3. **工作流是代码**：人事流程在 `apps/hr/services/` 中以代码实现，不做可视化编排。
4. **裁剪不删源码**：编排类功能仅从导航/路由隐藏，保留底层代码，便于跟随 MaxKB 上游升级。
5. **AgentKB 是参考实现**：现有 FastAPI/React 代码转为业务规则、状态机与验收测试的参考来源，不再扩展其知识库能力。

## 仓库策略

- Fork MaxKB `v2` 分支作为主仓库，提交人事模块代码。
- 记录 GPL-3.0 合规边界：衍生代码须开源，产品内不得闭源额外授权。
- 旧 AgentKB 仓库保留为只读参考，不删除（数据迁移与测试用例来源）。

## 子项目边界

本规格是整体路线图，拆分为三个独立子项目，各自经历"规格 → 计划 → 实现"周期：

1. **子项目一（第一阶段）**：MaxKB 精简内核 + 人事模块骨架。首个实现计划只覆盖此范围。
2. **子项目二（第二阶段）**：人事业务完整迁移（候选人/职位/指派/面试/Offer 状态机与 Vue 页面）。
3. **子项目三（第三阶段）**：简历结构化与智能搜人迁移（复用 MaxKB RAG 与模型能力）。

子项目一完成后，再对子项目二单独校验需求与设计。

## 第一阶段：MaxKB 精简内核

目标：得到干净的"知识库平台内核"，可独立部署验证。

范围内保留：

- 工作区、用户、角色权限
- 模型管理（LLM / Embedding / Rerank 配置）
- 知识库、文档上传、分块、向量化
- 知识库问答、来源引用、会话管理
- MaxKB 现有 Vue 管理后台

范围外（隐藏入口，不删除代码）：

- 可视化工作流编排
- MCP 工具
- 函数库
- 应用市场 / 应用模板
- 工作流应用发布

验收标准：

- 精简版可 Docker 部署，知识库上传与问答流程可用。
- 编排类入口在导航中不可见。
- 不删除、不修改 MaxKB 既有公共接口与核心代码，隐藏仅通过配置/路由层实现，保证上游 `v2` 升级可合并。

## 第二阶段：人事模块 apps/hr

在 MaxKB 的 `apps/` 下新增独立 Django app：

```text
apps/hr/
├── models/
│   ├── candidate.py     候选人（含简历解析结果、PII 加密）
│   ├── job.py           职位（HC、状态）
│   ├── assignment.py    指派（招聘流程状态 + 面试结果）
│   └── interview.py     面试轮次与反馈
├── api/                 人事相关 URL 与视图
├── services/
│   ├── resume_parser.py     简历上传→解析→结构化→画像
│   ├── talent_search.py     自然语言→意图→检索→排序
│   ├── interview_workflow.py 安排→反馈→通过/不通过/未履行/取消
│   └── offer_workflow.py    发Offer→入职/拒绝→HC 更新
├── migrations/
└── (前端) Vue 页面 + 菜单"人事部"
```

`apps/hr/services/` 即"代码级工作流"：流程由代码与测试保证，无工作流表、无拖拽、无 MCP。

状态模型沿用已批准的 AgentKB 设计：

- 招聘流程：`pending_screen → screen_passed → interviewing → offer → hired`，终态 `rejected / offer_rejected / closed_*`。
- 面试结果：`passed / failed / no_show / cancelled`，独立于流程状态。
- 面试通过不自动发 Offer；发 Offer 后可入职或拒绝。

## 第三阶段：能力复用矩阵

| 人事需求 | 复用 MaxKB | apps/hr 补充 |
|---|---|---|
| 简历上传 | 文件存储、文档解析、模型管理 | 简历字段提取、PII 脱敏、人才画像 |
| 人才搜索 | Embedding、Rerank、向量库、模型调用 | 候选人条件、职位匹配、状态过滤、意图路由 |
| 知识库问答 | 分块、RAG、引用、多轮对话 | 人事知识库模板、招聘政策问答 |
| 权限 | 用户、团队、工作区 | HR / 面试官 / 管理员业务权限 |
| AI 调用 | 模型供应商与配置 | 人事提示词与结构化输出 Schema |

## 迁移顺序

1. Fork MaxKB `v2`，确认 GPL-3.0 使用边界。
2. 隐藏工作流 / MCP / 函数库 / 市场入口（导航与路由层）。
3. 在 MaxKB 中新增"人事部"菜单与空的 Django/Vue 模块骨架。
4. 迁移候选人、职位、指派、面试、Offer 状态机（数据模型 + API + 页面）。
5. 迁移简历结构化解析与 PII 脱敏（复用 MaxKB 解析管道，自定义结构化逻辑）。
6. 迁移自然语言搜人（意图路由自研，检索底座复用 MaxKB RAG 与模型能力）。
7. 旧 AgentKB 提供业务规则、测试用例与数据迁移来源。

## 不做的内容

- 可视化工作流编排引擎
- MCP 工具接入
- 函数库
- 应用市场 / 应用模板
- 在 AgentKB 上继续扩展知识库/问答能力

## 执行环境

- 子项目一在 MaxKB fork 仓库中执行（新增 `hr` app 骨架与隐藏配置），当前 AgentKB 仓库只读。
- 未在规格中列出的 MaxKB 具体文件路径与菜单结构，由实现计划阶段探索 `v2` 分支后确定。

## 验收与测试

- 第一阶段：精简内核可部署，知识库上传/分块/问答/引用全链路可用，编排入口不可见。
- 第二阶段：候选人/职位/指派/面试/Offer 全流程在 MaxKB 内可用，状态机与 AgentKB 测试用例一致。
- 第三阶段：简历结构化与搜人质量不低于 AgentKB 现有水平（沿用既有评测数据集）。
- 全流程回归：以 AgentKB 现有测试作为行为基准，迁移后逐项对照。
