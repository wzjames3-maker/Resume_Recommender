## 1. 产品概述

**一句话定位**：

- **平台定位（技术视角）**：以 MaxKB v2 fork 为内核的多租户知识库 + RAG 平台。企业客户在平台上维护自己的知识库，人事场景以代码级业务模块（Django app `apps/hr`）接入，后续财务、法务、运营、售前客服、售后客服以同样方式逐个扩展，服务其内部员工或外部客户。
- **业务定位（客户视角，首发场景）**：**企业 AI 招聘大脑**——AI 人才库、智能搜人、岗位匹配、招聘流程自动化、人才资产沉淀。产品的核心价值不在 RAG 本身，而在把招聘业务对象（人才、岗位、流程、反馈）建模成业务模块可理解、可操作的世界模型，并从"简历搜索"升级到"人才理解与招聘决策"。
- **目标客户（MVP）**：**企业内部人事部门整体**。不按 HR、招聘专员、人事专员、面试官等岗位拆分业务权限，人事部门成员统一使用招聘工作台；「面试官」仅为面试任务上的负责人字段。"面试官搜库权限"等岗位级权限问题明确不做（见 §4）。

**产品形态**：toB 多租户 SaaS。

**核心价值**：

| 角色 | 痛点 | 平台价值 |
|------|------|----------|
| 企业管理员 | 通用大模型不了解企业私有知识，回答不可控 | 基于企业私有知识库的 RAG，回答带引用、可审计 |
| HR / 招聘团队 | 筛简历靠人肉翻，招聘流程（找人→面试→反馈）割裂在多个系统里，面试反馈记录了但不可用 | AI 招聘工作台：简历自动解析入库（含三层 AI 人才画像）、对话式搜人、一键批量加入待面试表、AI 对比决策辅助、面试官反馈闭环 |
| 业务员工 / 客户 | 政策、流程、产品问题要找人问，响应慢 | 7×24 即时问答，带来源引用 |
| 平台方（我们） | —— | 一套底座支撑六个场景，场景以"编排配置"方式扩展 |

## 2. 背景与问题定义

1. MaxKB 类产品验证了"知识库 + 对话问答"的企业需求，但只提供了**单一问答形态**，缺少面向业务场景的 Agent 编排（意图识别、工具调用、多轮记忆、场景化工作流）。
2. 参考项目各自验证了单一场景的可行性：
   - Resume_Recommender：人事招聘 RAG（意图路由、混合检索、PII 脱敏）
   - legal-assistant：法务 Agentic RAG（结构化输出、人工审核闭环）
   - Customer-Agent：客服 Agent（工具调用、双知识库、转人工）
3. 市场缺的是**把这些场景能力沉淀为可复用平台**的产品：企业不用为每个部门单独采购/开发一套系统。

**本产品的差异化**：MaxKB 内核（知识库管理 + 检索内核 + 多租户）与业务模块解耦；新场景接入 = 在 MaxKB 内新增一个代码级业务模块（Django app）并挂载知识库能力，而不是重新开发一套系统。

## 3. 目标与成功指标

### 3.1 阶段目标

| 阶段 | 目标 | 衡量标准 |
|------|------|----------|
| MVP（本期） | MaxKB 精简内核 + 人事业务模块跑通完整闭环 | 见第 7 节验收口径 |
| V1.1 | 接入第 2、3 个场景（售后客服、售前客服） | 验证代码级业务模块的场景扩展性 |
| V1.2 | 财务 / 法务 / 运营场景 + 配额计费 | 商业化闭环 |

**MVP 核心价值优先级**（v0.26 延续 v0.24 决策）：

1. **简历解析质量**：能否准确理解简历，结构化字段准确、不编造。
2. **搜人质量**：人事部门能否通过自然语言找到符合条件的人。

招聘流程协同（管道/待面试/面试反馈/三池）为支撑闭环，可进入 P0 范围但不作为本阶段核心价值判断依据。两项核心指标的评测规则见《简历解析质量评测》与《搜人质量评测》spec（§13.3）。

### 3.2 北极星指标（MVP 后观测）

- 租户工作区的周活跃 Agent 对话数
- 简历场景：单次对话内检索命中率（用户未换说法重试即采纳答案的比例）

## 4. 目标用户与角色

### 4.1 客户画像

中小到中大型企业的 HR 部门、客服团队、知识管理团队；单个租户规模从几十人到上万人不等。**平台总用户量级目标：10K（跨租户累计注册用户）。**

**MVP 目标客户**：企业内部人事部门整体。人事部门内部不按岗位拆分业务权限；业务部门负责人、外部面试官、跨部门协作不在 MVP 范围（见 §9 边界）。

### 4.2 角色定义

| 角色 | 作用域 | 说明 |
|------|--------|------|
| **平台管理员**（superuser） | 平台 | 平台运营方，查看全局用量与健康状态 |
| **工作区 owner** | 租户 | 企业创建者，管理工作区与成员 |
| **工作区 admin** | 租户 | 维护知识库、模型配置、Agent 配置 |
| **工作区 member** | 租户 | 使用 Agent 对话（如 HR 专员搜简历、员工问政策） |

> **权限模型原则**：
> 1. 工作区角色沿用 MaxKB 内核（owner/admin/member + superuser）不变，只区分"管理权"与"使用权"；
> 2. **同一部门/场景内不设角色细分**——招聘场景中 HR、人事专员、面试官权限完全相同，"面试官"只是面试任务上的负责人字段（指派谁填反馈），不是角色，不产生权限差异；
> 3. **不同部门（场景）的权限边界**在 V1.1+ 多场景接入时按场景/Agent 配置边界划分（MVP 只有招聘一个场景，天然不涉及）；
> 4. **口径澄清（v0.26）**：第 2 条"不设角色细分"指**招聘业务层**（搜人、查看候选人、上传、指派、状态流转等）；底座层的 owner/admin/member 管理权差异（模型配置、职位编辑/关闭、入职员工库查询等）属于**平台基础管理权限**，不属于岗位级招聘权限，两者不冲突。

### 4.3 典型用户故事（MVP）

- **US-1**：作为招聘专员（member），我把一批候选人简历（doc/docx/txt/csv/json）批量上传，系统自动解析、结构化入库，无需人工录入；PDF 等其他格式上传时被直接拒收并提示转换。
- **US-2**：作为招聘专员（member），我说"帮我找 5 年经验的 Java 后端，base 杭州"，系统返回按相关度排序的候选人卡片列表，并标注每个人的匹配依据。
- **US-3**：作为招聘专员，我追问"学历高一点""范围缩小到上海"，系统在上一轮条件基础上收敛，不需要我重复已有条件。
- **US-4**：作为招聘专员，我把两三个候选人加入对比，查看结构化字段并排对照，决定进入面试的人选。
- **US-5**：作为企业管理员（owner），我填入自己的 DeepSeek API 地址和 Key，平台默认用 DeepSeek 做生成、bge-m3 做向量化，模型成本由我方承担、数据链路可自查。
- **US-6**：作为招聘专员（member），我创建职位"Java 后端 P6 · 杭州 · 招 2 人"后，Agent 主动告诉我"人才库中有 12 位候选人可能匹配，要我列出来吗？"。
- **US-7**：作为 HR 负责人，我说"列出曾拒绝我们 offer 的候选人"，系统基于**指派记录历史**（F15 语义澄清）返回名单，并标注其当前池归属（已面试未通过库或仍在企业人才库）；如需清理，在列表勾选后批量删除（软删除，30 天内可恢复）。
- **US-8**：作为招聘专员，我点候选人卡片上的"加入待面试"按钮（或在搜索结果表格视图勾选多人批量加入），选择职位后候选人即进入该职位的招聘管道。
- **US-9**：作为某场面试的面试官（被指派的 member，权限不变），我在站内待办收到面试任务提醒，填写评分、结论（进下一轮/推荐发 offer/淘汰/待定）和评语；超 48 小时未填会再次提醒。
- **US-10**：作为招聘专员，我打开候选人时间线，能看到全部状态变化、各轮面试反馈和我的沟通备注（"已电话沟通，候选人考虑中"）。
- **US-11**：作为招聘专员，我说"我需要 50 个会 SpringBoot 的人"，Agent 返回按相关度排序的候选人（卡片带匹配依据）；结果在工作台表格视图呈现，我勾选后批量加入 Java 后端职位的待面试表；若批量加入时未选职位，界面提示选择并按能力匹配推荐在招职位。
- **US-12**：作为招聘专员，我说"我需要 20 份匹配当前岗位前端开发的简历"，Agent 自动从岗位管理调出"前端开发"岗位的自然语言要求，解析为检索条件后查询人才库，返回按相关度排序的 20 份简历。
- **US-13**：作为 HR 负责人，我说"在已面试未通过的人才库里查一下有没有做过电商运营的"，Agent 单独检索该池并返回结果；而日常任何普通搜人都不会混入已面试未通过或已入职的候选人。

## 7. MVP 详细需求

### 7.1 平台底座（P0，基于 MaxKB v2 fork 精简内核）

> 平台底座 = MaxKB v2 fork 的**精简内核**：保留知识库/问答/权限/模型能力；隐藏工作流编排、MCP、函数库、应用市场、应用发布（导航与路由层隐藏，不删除源码，保证上游 `v2` 升级可合并）。人事业务作为 MaxKB 内定制模块，见《MaxKB 人事模块化改造》spec。

#### F1 认证与租户（沿用 MaxKB 设计）

- 邮箱密码注册 / 登录；JWT access_token（30min）+ refresh_token（7 天）
- 工作区创建、按邮箱邀请成员、角色管理（owner/admin/member）
- 跨租户隔离：非成员访问资源一律 404，不暴露资源存在性

#### F2 模型配置（复用 MaxKB 模型管理并强化约束）

- admin 在工作区级别配置模型接入（复用 MaxKB 模型管理能力，按本方针强化：）
  - LLM：API Base URL + API Key + 模型名（默认预填 DeepSeek 官方地址与 `deepseek-chat`）
  - Embedding：API Base URL + API Key + 模型名（默认预填 bge-m3 兼容服务）
  - Rerank：API Base URL + API Key + 模型名（默认预填第三方 `bge-reranker-v2-m3`）
- Key 加密存储（AES-256-GCM），API 响应中永不回显完整 Key（仅显示前 8 位掩码）
- 模型配置生成不可变 `model_config_revision`；连接测试与生产调用统一经过出站网关：仅允许 HTTPS，阻断 localhost、回环、私网、链路本地、云 metadata 地址和非允许端口；DNS 解析后再次校验 IP，禁止跨域重定向；记录脱敏后的 endpoint、配置 revision、状态和耗时。
- 提供"连接测试"按钮：分别验证 LLM structured output、Embedding 维度/距离度量、Rerank 请求协议与分数方向；响应大小、超时、并发和重试受网关限制，API Key 支持轮换且不进入日志。
- Embedding 模型必须返回 1024 维（或在创建新的索引 profile 后明确迁移）；向量索引绑定 `model_config_revision` 与 embedding profile。模型切换必须新建索引、完成回归验收后原子切换，旧索引在切换完成前只读保留。
- 平台不代付模型费用，不提供平台级模型池（MVP 边界）

#### F3 知识库管理（沿用 MaxKB 设计）

- 知识库 CRUD、文档上传（md/txt/pdf/docx，≤50MB）、Celery 异步解析
- 文档状态机：pending → processing → ready / failed（可 retry）
- 分块策略：chunk_size / chunk_overlap 创建时指定，创建后不可变
- 分块查看（member 可读）

#### F4 检索内核（增强）

- MaxKB 原有：pgvector 向量检索（bge-m3，1024 维，HNSW 索引）
- 增强：混合检索 = 向量检索 + 全文检索（PG 中文分词或 trigram），RRF 融合 + rerank（第三方 `bge-reranker-v2-m3`，经租户配置的 rerank API 调用）
- 检索以内部 API 形式同时服务通用问答与人事业务模块

#### F5 通用对话（沿用 MaxKB 设计）

- 针对知识库的直接问答（SSE 流式、引用来源、会话管理）
- 该能力直接来自 MaxKB 内核，是业务模块可复用的最小问答形态

### 7.2 人事 · AI 招聘工作台场景（P0）

#### F6 简历解析与入库流水线

| 步骤 | 说明 |
|------|------|
| ① 上传 | 批量上传 doc/docx/txt/csv/json（单次 ≤100 份，单份 ≤20MB；csv/json 使用《简历 Schema 与导入模板》spec §3 的 envelope，批次级必填 `source_channel`（`referral` / `job_site` / `headhunter` / `campus` / `other`）/ `template_version`，平台提供导入模板）。**格式限定仅针对简历**，不影响 F3 知识库文档的格式支持 |
| ② 文本抽取 | **主力 + 兜底双通道策略**（调研结论：无单一库能覆盖全部 Word 排版形态）：**主力通道**——结构化抽取器（默认 python-docx 三通道：正文段落 + 全部表格 + 文本框 XML 遍历；表格型是国内简历主流形态），产出带类型标记的块流（段落/表格/文本框，保留阅读顺序），**抽取器保持接口抽象，正式 holdout 评测前在 dev 集完成候选解析器选型（Docling / MegaParse / ZhDocParser 等）；holdout bundle 冻结后 parser/converter 版本不可变**；**兜底通道**——主力抽取有效字符低于阈值、或文件为 .doc 旧二进制格式时，走 LibreOffice headless（`soffice --headless --convert-to docx/html`）转换后重抽，其排版引擎级渲染可靠覆盖文本框、分栏、嵌入对象与 .doc 格式（全 Python 生态无其他可靠 .doc 方案）；**不做 OCR**，不支持的格式（含扫描件）上传时直接拒绝并提示转换格式 |
| ③ Markdown IR 归一化 + 有效性校验 | 文档抽取产物**不直接送 LLM，先归一化为 Resume Markdown IR（文档理解层交换格式，非存储格式）**：YAML 元数据头（来源渠道/解析通道/解析时间）+ 章节式正文；表格保留 markdown 表格语法不展平；**IR 落库持久保存作为审计产物**（见下方"解析审计链"）；doc/docx/txt 抽取后的 IR 有效字符低于下限（冻结为 200，见《简历解析质量评测》spec §2.5）则标记 failed，不进入后续 LLM 调用。csv/json 走结构化导入校验，不以 JSON/CSV 语法字符数判断 IR 失败；由结构化字段与 `import_summary` 生成 IR/检索文本，字段为空时允许入库但标记「可检索内容不足」 |
| ④ PII 识别与脱敏 | **在任何外部模型调用之前执行**：按 taxonomy 识别手机号/身份证/邮箱、姓名、地址及自由文本中的联系方式；识别失败、映射缺失或脱敏失败时 fail-closed，不发送请求。原文只在本地完成结构化映射，外发使用加密 token；在用户对当前池及对象有读取权限的前提下可见原文，MVP 不做同池内展示级掩码与按岗位还原。**出站链路覆盖（正式约定）**：结构化、人才画像、embedding、rerank、AI 对比分析、面试反馈 AI 总结等**全部外部模型调用**统一经脱敏网关；全文索引、prompt/response、trace 和缓存不得写入明文 PII |
| ⑤ LLM 结构化（两阶段） | 输入 IR，调用租户配置的 LLM 分两阶段：**阶段一结构识别**（判断教育/工作/项目/技能等章节边界）→ **阶段二 Schema 抽取**（按统一简历 Schema 输出，**参照业界成熟的 18 字段标注体系补全**：基本信息——姓名/出生年月/性别/电话/最高学历/籍贯/政治面貌等；教育经历——毕业院校/学位/毕业时间**按组结构化**；工作经历——工作单位/工作内容/职务/工作时间按组；项目经历——项目名称/项目责任/项目时间按组；另含技能标签、期望职位）；原文作为不可信数据隔离传入，不允许模型调用工具或外部资源；输出必须通过版本化 JSON Schema、类型/枚举/日期/长度/未知字段和 evidence 引用校验，校验失败重试一次后进入 `failed`，不得以空对象伪装成功；无法确定的字段标 `null`，禁止编造；两阶段可合并为单次调用，由技术设计按 token 成本与准确率实测确定；**csv/json 导入已是结构化数据，跳过本步直接映射到统一 Schema（不重复过 LLM）** |
| ⑥ AI 人才画像 | 基于结构化结果由 LLM 生成**三层人才画像（Talent Intelligence）**：**第一层 固定画像（八维枚举，岗位中立）**——职级层级（Junior/Mid/Senior/Staff/Principal）、专业深度（Low/Medium/High/Expert）、领域经验（金融科技/电商/AI/医疗/供应链等枚举）、影响范围（个人贡献者/小组/团队负责/跨团队/组织级）、管理能力（无/导师/技术负责/团队管理/总监级）、职业稳定性（稳定/正常/频繁变动/风险）、成长趋势（上升/平稳/平台期/下滑）、沟通协作（低/中/高）——枚举可筛选可统计可匹配；**第二层 AI 开放洞察**——优势 strengths / 风险 risks / 职业模式 career_pattern 的自由文本，仅供 HR 阅读参考、不进检索条件；**第三层 岗位动态匹配**不在本步入库时生成（见下方注记）；输出必须通过版本化 JSON Schema 与 evidence 校验，无依据时生产字段返回 `null`（评测标注专用 `unknown` 不落库），非法结果不得入库；存候选人表画像字段（JSONB），**所有结论必须有简历依据、禁止编造**；固定层准确率按评测 spec §4.4 抽检口径观测（**参考观测指标**，不阻断解析/搜人两项核心门槛）；开放层抽检 |
| ⑦ 入库 | 结构化字段 + 人才画像写候选人表（PII 字段此时加密落库，手机/邮箱另存哈希供查重）+ **分层向量化（按摘要/教育/工作/项目/技能五段 embedding，支持"找做过支付系统的人"主要命中工作/项目段）** + 全文索引 |

- **解析审计链（企业级刚需）**：每份简历持久保存 `原文件 → Markdown IR → candidate.json（结构化字段）→ 人才画像（固定层+洞察层）` 四级产物，并记录 `run_id`、revision_id、各产物 hash、解析器/模型/提示词/schema 版本、配置快照、evidence block/span、人工修正前后值；匹配推荐时可回溯"AI 为什么认为这个人适合"（matching_reason 只能引用同一 revision 的 evidence），HR 可质疑、可追溯、可重跑
- **文件解析安全**：上传校验文件签名/MIME 与扩展名一致；加密、宏、嵌入对象和压缩炸弹默认拒收（不进入 LibreOffice；除非未来增加明确的安全净化流程）；文件先经过恶意文件扫描，再置于无网络、低权限、资源受限的隔离环境转换；单文件解压后 ≤100MB、XML 深度 ≤100、嵌入对象 ≤20、CPU ≤60s、内存 ≤1GB、临时磁盘 ≤500MB、转换输出 ≤50MB、worker 并发按租户限流；临时目录任务结束后清理并记录失败原因
- **幂等与可重跑**：同一次上传使用 `workspace_id + upload_id`，同一业务输入使用 `workspace_id + 文件内容 hash + 导入模板版本 + source_channel`；显式重解析必须生成新的 `run_id / revision_id`，CSV/JSON 重试按 `row_hash` 仅处理失败行。Celery 至少一次投递 / worker 重启 / 重试均不产生重复候选人、解析产物或索引写入；所有 UI 写命令使用客户端 `idempotency_key`，响应可重放；重试不重复扣费、不覆盖已发布版本（详见《简历 Schema 与导入模板》spec §3.4）
- **第三层 岗位动态匹配（Candidate × Job）**：不预存全量候选人×职位组合，仅在匹配推荐/按岗位搜人/指派触发时惰性计算 match 度与 reason 依据；分数仅用于后台排序与 AI 对比分析，前端延续"不展示数值分数"决议（只展示相关度顺序与匹配依据）
- 解析任务走 Celery，前端显示批量任务进度（成功/失败/进行中）
- 解析失败可查看原因并单独重试；错误分类为不可重试（格式/安全/Schema）与可重试（超时/限流/暂时网络错误），最多自动重试 2 次、指数退避；人工 retry 生成新的 run_id，不覆盖已发布 revision，连续失败进入 dead-letter 状态等待人工处理
- **M3 验收样本集使用 AI Studio 合成公开数据集（简历信息抽取数据）**，覆盖表格型/文本框型/.doc 旧格式/脏数据（字段矛盾/时间线混乱）四类，验证"无法确定标 null、禁止编造"规则的健壮性；数据集来源、样本构建与评测细则见《简历解析质量评测》v0.4 spec（v0.24 决策：原"自建真实样本"改为使用该公开数据集）
- **查重**：规则见 F12（在解析后、入库前执行）；查重与池归属的联动见 F15

#### F7 对话式搜人（核心）

代码级工作流（实现于 `apps/hr/services/` 意图路由模块，不做可视化编排）：

```
用户输入 → 意图识别（搜索 / 按岗位搜索 / 追问收敛 / 统计查询 / 写请求引导 /
                    闲聊 / 超出范围）
        → 搜索意图：条件抽取（技能、年限、城市、学历、行业、画像维度（职级层级/领域经验/稳定性等固定枚举）、数量 top-N…）
                   → 与上轮条件合并（上下文记忆）
                   → 混合检索 + rerank
                   → 按 rerank 相关度降序生成候选人卡片（命中条件标注）+ SSE 流式输出
        → 按岗位搜索意图：定位目标岗位（名称或会话上下文）→ 调取岗位要求
                   → 解析为检索条件 → 合并指令附加条件（数量等）→ 走检索链路
        → 追问意图：仅更新变化字段，重走检索
        → 统计查询：结构化统计卡片（见 F11）
        → 写请求引导：识别写意图（打标/修正/删除/指派等）→ 不执行，引导到工作台 UI 操作（见 F11）
        → 超出范围：明确拒答并引导
```

- **搜索范围**：默认且仅覆盖企业人才库；已面试未通过库/入职员工库必须用户显式指定才可检索（见 F15），Agent 绝不主动跨池混入结果
- 多轮记忆：同一会话内条件累积与修正（"再推几个""学历高一点"）
- **数量意图（top-N）**："我需要 50 个会 SpringBoot 的人"抽取 N=50，按相关度降序返回；匹配不足 N 人时返回实际命中数并说明，建议放宽哪个条件，不凑数、不编造
- **按岗位搜索**："我需要 20 份匹配前端开发岗位的简历"→ 定位目标岗位（按名称或会话上下文）→ 调取该岗位的自然语言要求（F10）解析为检索条件 → 合并指令中的附加条件（数量、额外技能）→ 执行检索；定位不到岗位时反问确认
- **排序与可解释**：结果统一按 bge-reranker-v2-m3 重排后的相关度顺序展示，**不展示数值分数**（rerank 原始分数无稳定业务含义，硬映射成分数会误导）；每个候选人卡片标注命中的具体条件作为匹配依据
- **大批量结果展示**：N 较大（>10）时，对话区展示摘要（命中数、前几名卡片），全量结果自动在工作台面板的表格视图呈现，支持勾选批量操作
- 意图误判纠正：用户说"不对，我要的是……"时回滚上一轮状态并重新路由，不带错误状态继续执行
- 无结果时给出建议（放宽哪个条件），不编造候选人

#### F8 候选人管理

- 列表页：按解析状态、技能标签、城市、学历、工作年限、来源渠道、流程阶段、**人才池归属**、**画像维度（职级层级/领域经验/稳定性等固定枚举）**筛选
- 详情页：结构化字段 + **人才画像卡片（固定八维枚举标签 + AI 开放洞察：优势/风险/职业模式）**+ 原文对照查看（仅当前用户对候选人当前池/对象有读取权限时可见；同一可见范围内 MVP 不做展示级掩码）
- 多人对比：最多 4 人并排对比结构化字段；可触发 **AI 对比分析**（招聘决策辅助）：结合岗位要求（若已选定职位）生成每人的优势/风险对比与场景化推荐（"若目标是技术专家 → A；若目标是带团队 → B"），回答"为什么选他"而不只是"找到谁"
- **候选人生命周期**：`active` → `deleted`（软删除，30 天可恢复）→ `purged`（硬删除/加密擦除，保留不可逆 tombstone）。软删除立即从列表、搜索、推荐和导出移除，但原文件、IR、revision、画像、向量、指派与审计关系保留；有进行中指派时默认拒绝删除，除非先完成合法关闭/终态处理。恢复必须在同一事务/可靠事件链中恢复可见状态并重建索引，硬删除后不得重新命中原候选人身份。
- 编辑修正：member 及以上可手工修正解析错误的字段（修正结果优先于解析结果，与候选人编辑删除权限同口径，见 F9）
- **候选人时间线**：状态流转、面试安排与反馈、沟通备注（HR 手动添加）按时间倒序留痕

#### F9 场景权限

- 简历上传 / 候选人编辑删除：工作区 **member 及以上**（上传是招聘专员的日常操作，与职位创建同口径放开；删除保留可撤销兼容机制，见 F11）
- 搜人对话 / 查看候选人 / 人才库查询：工作区 member 及以上
- 场景内不设角色细分：招聘专员与面试官权限完全相同，"面试官"仅是面试任务的负责人字段；MVP 不做简历安全的差异化权限管控（不考虑简历防扩散）
- 人才池查询权限：企业人才库与已面试未通过库 member 及以上可查（后者需显式指定）；入职员工库涉及员工信息，仅 admin 及以上可查
- 简历数据严格租户隔离，跨租户不可见、不可检索
- **角色继承**：owner 继承 admin 的业务资源权限；superuser 仅用于平台运维，不默认获得租户候选人原文、PII 或员工池访问权，除非有明确的审计授权。
- **服务端权限强制校验（正式约定）**：全部写操作与数据访问在服务端按 workspace / 角色 / 对象状态 / 目标池校验；UI 隐藏按钮仅作体验层，不作为权限边界；内部 API 与异步任务强制传递并校验 workspace context，禁止客户端自行声明池/租户参数。
- **最小权限矩阵**：候选人列表/详情/原文件/IR/画像读取、字段修正、删除/恢复、合并、指派、面试安排、反馈修改、AI 总结、关闭余下指派、职位编辑/关闭、员工池查询、历史指派查询均为独立服务端动作；未在矩阵中明确允许的动作默认拒绝。历史条件查询先按 `allowed_pool_scopes` 过滤，再执行 assignment history，member 不得通过计数、是否命中、池名或错误信息获知员工池候选人。

| 资源 / 动作 | owner | admin | member | 约束 |
|--------------|-------|-------|--------|------|
| active/rejected 候选人列表、详情、原文件、IR、画像 | 允许 | 允许 | 允许 | 必须是当前池可见对象；跨租户统一 404 |
| hired 候选人及其原文件/IR/PII | 允许 | 允许 | 拒绝 | 拒绝不得泄露存在性、数量或池名 |
| 简历上传 / 导入 / 解析重试 | 允许 | 允许 | 允许 | source_channel、文件安全、upload/run 幂等校验 |
| 候选人字段修正 / 删除 / 恢复 / 合并 | 允许 | 允许 | 允许 | 仅对可见且非进行中约束对象；进行中指派或 hired 默认拒绝删除/合并 |
| 指派 / 状态流转 / 面试安排 / 反馈 / AI 总结 | 允许 | 允许 | 允许 | 以对象池 ACL、机器状态、乐观锁和 idempotency_key 校验 |
| 职位创建 | 允许 | 允许 | 允许 | 创建者不能因此获得职位关闭权限 |
| 职位编辑 / 关闭 / 关闭余下指派 | 允许 | 允许 | 拒绝 | 关闭职位不允许新增指派；既有流程按 F13 规则处理 |
| hired 池查询 / assignment history | 允许 | 允许 | 仅可查询可见 active/rejected 对象的历史 | 历史谓词先 ACL 后执行，不得侧信道泄露 |
| 审计事件查询 | 允许 | 允许 | 拒绝 | superuser 需显式租户审计授权；内容只返回脱敏值/hash |

#### F10 职位管理（简化版）

- 职位字段：名称、**岗位要求（自然语言描述**，如"5 年前端开发经验，精通 Vue/React，有大型项目经验"）、招聘人数、城市、薪资范围（可选）、状态（招聘中/已关闭）
- 岗位要求**不强制结构化填写**，自然语言描述即可；匹配/检索时由 LLM 将要求描述解析为检索条件（技能/年限/学历等），解析结果在对话中可见、可人工纠正
- **职位创建：member（人事部门）及以上；职位编辑/关闭：admin 及以上**（创建是招聘专员的日常操作，放开到使用层；关闭职位影响在职流程，保留在管理层）
- **岗位要求版本化**：岗位自然语言描述每次变更生成 `job_requirement_revision`；LLM 解析结果保存为严格条件 AST，人工修正作为字段级 override，均记录模型/prompt/schema 版本和岗位描述 evidence span；未出现在岗位描述或明确人工 override 中的条件不得加入 AST。匹配缓存绑定 `job_id + job_requirement_revision + candidate_revision + model/index revision`，任一依赖变更即失效。
- **职位定位**：按 `job_id` 执行匹配；同名/近似名职位只能展示候选职位供用户选择，未确认时不得按名称猜测。
- **能力匹配是本场景的核心能力，且是双向的**（人才库简历来自猎头/网站/内推/历史沉淀，普遍没有投递岗位信息，匹配靠能力而非投递记录）：
  - 职位 → 人（主动触发）：创建职位后 Agent 主动匹配人才库，在对话区提示"有 N 位候选人可能匹配，要我列出来吗？"
  - 职位 → 人（指令触发）："我需要 20 份匹配前端开发岗位的简历"→ Agent 自动调取岗位要求解析检索（见 F7 按岗位搜索意图）
  - 人 → 职位：候选人详情页展示"TA 可能适合的在招职位"（按相关度排序，同用检索+rerank 链路）
- 职位是待面试表（F13）与漏斗统计的锚点

#### F11 人才库自然语言查询（严格只读）

**Agent 严格只读**：对话中不执行任何写操作（打标/修正/删除/指派均不做）；所有数据变更与流程操作统一走工作台 UI（卡片按钮/表格勾选）。

| HR 说法示例 | 意图 | 系统行为 |
|-------------|------|----------|
| "人才库里有多少 Java 候选人？城市分布？" | 统计查询 | 结构化统计卡片（数量/分布） |
| "把 3 年没更新的简历标记为'待激活'" | 写请求 | 不执行：列出命中名单供查看，引导在候选人管理页手工打标 |
| "张三其实是硕士，改一下" | 写请求 | 不执行：引导到候选人详情页修正字段（member 及以上，见 F8） |
| "把拒绝过我们 offer 的人删掉" | 写请求 | 不执行：基于指派记录历史（F15 语义澄清）明示名单及其当前池归属，展示匹配名单，引导在列表中勾选批量删除 |

- **池范围规则**：查询与搜索遵循相同的人才池范围——默认只查企业人才库；请求池范围先与当前用户 `allowed_pool_scopes` 求交集，再执行历史条件（如"曾拒绝 offer"）的指派记录查询；不可访问员工池候选人不得通过结果、计数、池名或错误信息泄露。M4 先验收最小 `pool_scope` ACL，M5 再验收状态流转驱动的完整池变更（搜人评测 spec §2.1/§2.2）
- 删除/修正等数据变更全部为 UI 操作：软删除 30 天内可恢复（全局默认，不做租户级配置）；字段修正记录变更前值；全部写操作入审计日志（操作人、操作内容、影响对象）

#### F12 查重与来源记录

- 查重：在解析后、入库前按姓名 + 手机号/邮箱精确匹配（手机/邮箱以哈希值比对，归一化规则见《简历 Schema 与导入模板》spec §3.5）识别重复，提示合并；合并后的候选人以**最新简历的解析值 + 人工修正 override** 为准（人工修正永不自动覆盖，见 Schema spec §2），保留全部简历文件与历史记录。模糊查重（向量相似度）为 P1
- 来源渠道：内推 / 招聘网站 / 猎头 / 校招 / 其他，上传时必选，支持按来源筛选与统计
- 内推归属：来源为"内推"时可记录推荐人（工作区成员或员工姓名），作为后续内推奖励统计依据

#### F13 招聘管道与待面试表

核心模型：**人才库中的候选人无职位属性**（简历普遍没有投递岗位信息）；候选人×职位通过"指派/推荐"建立关系（加入待面试表即创建一条指派记录），每条指派记录独立走完整管道；同一候选人可同时或先后被指派到多个职位（如 Java 职位淘汰后转推测试职位）。

指派记录的状态机：

```
指派（加入待面试表，关联职位）→ 初筛通过 → 面试中 → offer → 入职
                                       ↘ offer 已拒绝
        ↘─────────── 任意阶段可淘汰（淘汰原因必填）───────────↙
（淘汰/拒绝仅结束本条指派记录；候选人池归属按 F15 规则变化——若无其他进行中指派则移入已面试未通过库，重新指派可再回企业人才库）
```

**状态机转移矩阵（正式冻结，服务端强制校验）**：

| 当前状态 | 允许动作 | 下一状态 | 前置与必填 |
|----------|----------|----------|------------|
| —（未指派） | 加入待面试 | 待面试 | 职位必填且职位在招、HC 未满；候选人可进入多个职位流程 |
| 待面试 | 初筛通过 | 初筛通过 | 人工操作 |
| 初筛通过 | 安排面试 | 面试中 | 面试安排完成（候选人 + 职位 + 面试官 + 时间） |
| 面试中 | 发 offer | offer | 当前面试轮反馈结论为 `recommend`，所有必填反馈已提交 |
| 面试中 | 淘汰 | 已淘汰 | 淘汰原因必填 |
| 待面试 / 初筛通过 | 淘汰 | 已淘汰 | 淘汰原因必填 |
| offer | 确认入职 | 入职 | 触发池流转（F15） |
| offer | 候选人拒绝 | offer 已拒绝 | 独立终态，不计淘汰 |
| 任意非终态 | 淘汰 | 已淘汰 | 淘汰原因必填 |
| 任意进行中状态 | 入职后关闭余下指派 | closed_after_hire | 仅入职事务中由 HR 执行；关闭原因、操作者、时间必填，不计淘汰 |
| 任意进行中状态 | 职位关闭后由 admin 关闭指派 | closed_by_job | 关闭原因、操作者、时间必填，不计淘汰；不触发 `rejected` 池 |

- **机器状态枚举（正式冻结）**：`pending_screen`（待面试）/ `screen_passed`（初筛通过）/ `interviewing`（面试中）/ `offer` / `hired`（展示文案“已入职”）/ `offer_rejected`（展示文案“offer 已拒绝”）/ `rejected`（展示文案“已淘汰”）/ `closed_after_hire`（入职后关闭）/ `closed_by_job`（职位关闭后关闭）。终态为 `hired`、`offer_rejected`、`rejected`、`closed_after_hire`、`closed_by_job`，不可再次流转，仅保留历史；`closed_by_job` 不计淘汰、不触发 `rejected` 池。
- **反馈枚举（正式冻结）**：`advance`（进下一轮）/ `recommend`（推荐发 offer）/ `reject`（淘汰）/ `hold`（待定）。`hold` 不改变指派状态；`advance` 只能创建下一轮面试，不能直接发 offer；`recommend` 只能在当前轮必填反馈完整时触发 offer。
- **多轮面试**：每一轮为独立 `interview_round`，具有 `round_id`、轮次、面试官、时间、状态、feedback_id；同一轮只能有一份当前有效反馈，修改产生新 revision 并保留历史。下一轮必须通过显式“安排面试”动作创建，不能由 feedback 写入隐式推进。
- **事务一致性**：状态流转、时间线留痕、池归属变化在同一事务/可靠事件链内完成；并发操作以指派记录乐观锁（revision）防覆盖。
- 关闭其余进行中指派：入职事务锁定候选人及其全部指派，HR 一键关闭；关闭不计入淘汰，仅结束该条指派记录，状态写入 `closed_after_hire`。

- **待面试表**：按职位看板查看；加入方式为 UI 操作：点候选人卡片"加入待面试"按钮，或在搜索结果表格视图勾选后批量加入（对话指令不做指派，见 F11 严格只读）
- **职位必填与澄清**：指派记录必须关联职位；批量加入时未选职位则界面提示选择，并按能力匹配推荐在招职位，不自行猜测
- **批量添加**：表格视图勾选多人批量加入；已在其他职位流程中的候选人标注提示（不阻断，由 HR 决定）；同一 `candidate_id + job_id` 只能存在一条未删除指派记录，UI 命令携带 `idempotency_key`，重复点击不得重复创建指派或时间线事件
- **职位阶段视图**：职位详情下按机器状态分组展示该职位的候选人列表（待面试 / 初筛通过 / 面试中 / offer / 已入职 / offer 已拒绝 / 已淘汰 / 入职后关闭），即"岗位下的待面试简历与面试过的简历"
- **流转与池归属**：指派记录结束后候选人的池归属变化统一按 F15 三池模型规则执行（含"仍有其他进行中指派则暂不移动"的例外）
- **HC 与职位关闭校验**：职位保存 `hc_total`、`hc_reserved`、`hc_filled`；`hc_filled = hired`，`hc_reserved = offer`（不含待面试/初筛/面试中候选人，允许建立候选人池）；加入待面试/初筛/面试中只允许 `hc_filled < hc_total`；从面试中进入 offer 时以职位行锁或原子条件更新保证 `hc_filled + hc_reserved < hc_total`，禁止并发超招。offer 拒绝释放 reservation，offer→hired 原子地将 reservation 转为 filled；淘汰/`closed_by_job` 释放未占用名额。职位关闭后不可新增指派或进入初筛，但已有 `interviewing` / `offer` 可继续完成或由 admin 转为 `closed_by_job`；关闭职位不可重新开放，需新建 revision/job_id。
- **"offer 已拒绝"为独立终态**（不计入淘汰），是 US-7 筛选"曾拒绝我们 offer 的候选人"等查询条件的数据支撑
- **淘汰原因**：下拉枚举（能力不匹配/薪资不符/候选人放弃/HC 取消/其他）+ 自由补充，沉淀复盘数据
- 状态流转与时间线（F8）联动，每次流转留痕

#### F14 面试安排与反馈闭环

- **面试安排（简化版）**：候选人 + 职位 + 面试官（从工作区 member 指派）+ 面试时间；不做日历集成（P2）
- **面试官视角**：面试官只是面试任务的负责人字段（从 member 中指派），不产生任何权限差异；首页/待办突出展示分配给自己的面试任务
- **结构化反馈（必填）**：评分（1–5）、结论（`advance` / `reject` / `hold` / `recommend`）、评语；多轮面试逐轮记录，汇总展示在候选人时间线；`recommend` 只允许当前轮次完整提交后触发 offer，`advance` 只允许创建下一轮。
- **反馈 AI 总结**：面试官填写自由评语后可一键生成结构化总结（优势 / 风险 / 建议），可编辑、保留原始评语；解决"反馈有记录但不可用"的痛点，让后续轮次面试官与 HR 能直接消费反馈
- **超时提醒**：每个 `interview_round` 48 小时未填写反馈 → 站内待办提醒；提醒使用 `round_id + reminder_type` 幂等，消息推送随 V1.1 渠道接入。

#### F15 人才池分区与流转（三池模型）

候选人按归属划分为三个互斥的池（实现为候选人上的池属性，非物理迁表）：

| 池 | 进入触发 | 默认搜索是否覆盖 |
|------|----------|------------------|
| 企业人才库（`active`） | 解析入库默认归属；重新指派时回到此池 | ✅ 默认且唯一的搜索范围 |
| 已面试未通过库（`rejected`） | 候选人无其他进行中指派，且结束的指派终态为 `rejected` 或 `offer_rejected` | ❌ 仅显式指定可查 |
| 入职员工库（`hired`） | 入职事务将当前指派置为 `hired`，并原子关闭其他进行中指派为 `closed_after_hire` | ❌ 仅显式指定可查 |

> 注：`rejected` 池实际包含当前没有进行中指派、且最后终态为 `rejected` 或 `offer_rejected` 的候选人；“曾拒绝 offer”是独立历史条件，不能假设所有命中者当前都在 `rejected` 池。
>
> **语义澄清（v0.26）**：人才池表示候选人的**当前归属**（互斥的单值），不承载历史流程分类。「曾拒绝 offer」「已入职」等历史条件通过**指派记录历史（assignment history）**查询，不依赖当前池——当候选人在 A 职位 offer 已拒绝、B 职位仍有进行中指派时，其当前池仍为企业人才库；当前池为 `hired` 的候选人只对 owner/admin 暴露，member 的历史查询先按 ACL 过滤，不得泄露员工池信息。

- **流转规则**：候选人及其全部指派按候选人锁原子计算当前池：存在 `hired` 指派时当前池为 `hired`；否则存在进行中指派时为 `active`；否则以最近一次**会改变池归属**的终态判断，`rejected` / `offer_rejected` → `rejected`，重新指派 → `active`，`closed_after_hire` / `closed_by_job` 保持关闭前池归属。入职时必须在同一事务中关闭其余进行中指派，任一步失败则整笔入职回滚；池变更后立即从默认搜人结果移除。
- **可逆性**：`rejected` 候选人可被 member 重新指派到其他职位，重新指派与池回到 `active` 必须同一事务完成；`hired` 候选人禁止重新指派，若未来允许返聘需新建独立候选人/返聘流程，不复用已入职指派。
- **查询规则**：普通搜人、按岗位搜人、创建职位后的主动匹配，一律请求 `pool_scope=active`；查询 `rejected` / `hired` 必须用户显式指定且通过服务端 ACL，Agent 不主动混入、不跨池推荐；历史条件先过滤可访问当前池，再执行 assignment history。`hired` 候选人禁止重新指派，`rejected` 候选人可重新指派回 `active`。
- **查重联动**：已在已面试未通过库/入职员工库的候选人被再次上传简历时，查重命中并提示其池归属与历史面试记录，由 HR 决定是否合并回企业人才库
- **时间线不变**：池流转记入候选人时间线，全部历史记录保留

## 8. 非功能需求

### 8.1 容量与性能（10K 用户量级）

容量测算（保守估计）：

| 指标 | 假设 | 数值 |
|------|------|------|
| 注册用户 | 跨租户累计 | 10,000 |
| DAU | 30% | ≈3,000 |
| 人均日对话 | 5 轮 | ≈15,000 轮/日 |
| 峰值系数 | 60% 集中在工作时间 4 小时内 | 峰值 ≈0.6 QPS 对话请求，并发 SSE ≈100 条 |
| 简历存量 | 每租户 10 万份上限 | 向量库总量 100 万级分段，pgvector+HNSW 可支撑 |

结论：10K 用户量级下瓶颈在 **LLM API 的并发配额与延迟**，而非平台自身。平台侧要求：

- API 无状态，可水平扩容；对话请求与文档解析分离（解析走 Celery 队列，不占对话链路）
- 平台自身接口 P95 < 500ms（不含 LLM 调用）；对话首 token 延迟 ≤ 3s（不含检索+LLM 自身耗时）
- LLM 网关层实现：并发控制、超时重试、按工作区限流、失败降级提示

### 8.2 安全与合规

- 多租户隔离：所有资源按 workspace_id 隔离，跨租户访问统一 404
- PII：建立统一 taxonomy（姓名、手机号、身份证、邮箱、地址、原文件、IR、自由文本中的联系方式）；原文件/IR/候选人字段/脱敏映射分层加密，embedding/rerank 只接收脱敏文本或非 PII 结构化片段；识别、映射或脱敏失败时 fail-closed，不向外部模型发送；哈希供查重
- API Key 加密存储，日志中禁止出现完整 Key 与简历原文
- **不可变审计事件**：所有读取/导出、权限拒绝、模型出站、模型配置变更、解析 run、人工修正、合并/恢复/清理、池流转、状态变更和 AI 输出均追加事件，至少含 `event_id/request_id/correlation_id/actor_id/workspace_id/resource_type/resource_id/action/result/before_hash/after_hash/run_id/revision_id/created_at`；审计值只存脱敏内容或 hash，审计读取仅 owner/admin，superuser 需显式授权。
- **数据生命周期**：候选人 `active → deleted（30 天可恢复）→ purged`；purged 对原文件、IR、revision、画像、向量、全文索引、临时文件和缓存执行级联删除/加密擦除，审计只保留 tombstone 与 hash。备份按同一生命周期延迟清理，legal hold 时暂停 purged。
- 个保法责任边界：候选人个人信息的授权同意义务由租户（企业）承担，平台在服务协议中明确；MVP 使用上述固定 30 天生命周期，租户级保留期配置与到期策略为 P1

### 8.3 可用性与运维

- 部署沿用 MaxKB 官方 Docker 方案（可独立部署验证精简内核）；人事模块随 Django app 内嵌，不新增独立服务；简历抽取兜底通道依赖 LibreOffice headless，随 worker 镜像内置（见 F6 ②）
- 健康检查端点、Prometheus 指标（沿用 MaxKB 内核能力）
- 文档解析任务失败按可重试/不可重试分类，最多自动重试 2 次、指数退避；dead-letter queue、人工 retry 新 run、临时目录清理和索引原子发布均可观测

### 8.4 可观测性

- 对话与解析链路埋点：意图分类分布、检索命中率、ACL 拒绝、解析各阶段成功率、队列深度/年龄、重试/DLQ、索引延迟、PII 脱敏失败、LLM 耗时与 token 消耗（按工作区/Agent 维度）；异常触发告警
- 该数据同时是后续配额计费的依据
