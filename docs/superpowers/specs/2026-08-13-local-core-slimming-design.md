# 本地开发内核裁剪设计

## 目标

将 MaxKB v2 fork 裁剪为可在本机安装依赖、检查后端、编译前端并继续开发人事模块的精简内核。Docker、生产守护进程和镜像优化不属于本轮目标，后续单独补齐。

## 保留范围

- 用户、工作区、成员角色与权限。
- 工作区级模型配置。
- OpenAI 兼容协议的 LLM 和 Embedding 调用。
- 知识库、文档上传、文档解析、分块、向量化和检索。
- 知识库问答、引用来源和会话管理。
- 必要的数据库、Redis、Celery 和 Django 基础能力。
- 后续 `apps/hr` Django 模块所需的扩展边界。

模型供应商统一通过 OpenAI 兼容协议接入。专用供应商 SDK 不再作为本地开发内核的依赖，也不保留对应的运行时 Provider。Rerank 本轮暂不支持，检索先按向量检索结果返回；后续接入明确的兼容服务时单独设计。

## 删除范围

实际删除代码、依赖、路由和配置，不仅隐藏入口：

- 本地模型服务及其启动分支、模型文件路径和重型本地推理依赖。
- 专用模型供应商 Provider、SDK、图标、注册项和配置页面，只保留 OpenAI 兼容的 LLM 与 Embedding 实现。
- 可视化工作流编辑器、工作流节点、MCP、工具编排、函数库、应用市场、应用模板和应用发布。
- 仅被上述能力使用的后端模块、任务、序列化器、URL、权限项和前端页面。
- 仅被已删除页面使用的 LogicFlow、CodeMirror、Cron、Mermaid、DingTalk、录音、PDF 导出等前端能力及依赖。
- Docker、installer 和生产启动相关内容暂不作为本轮裁剪目标；不为它们新增兼容代码。

## 架构边界

当前 MaxKB 将知识库问答与 application 目录部分共用，因此不能直接删除整个 `apps/application`。裁剪时保留知识库问答实际依赖的最小执行路径，删除独立的可视化编排和工具路径。删除后，保留代码不得通过动态导入、自动注册或前端 glob 间接引用已删除模块。

后端的 Django `INSTALLED_APPS`、URL 配置和任务自动发现列表只注册保留模块。前端路由和菜单只包含保留能力；构建配置不再解析已删除目录。

## 分阶段实施

### 阶段一：依赖与引用闭包

建立后端 Python 包、Django app、URL、Celery 任务和前端 npm 包的引用清单。每个删除项必须满足：不在保留链路的导入闭包中，且不被配置、自动发现或动态 import 引用。

### 阶段二：后端裁剪

先移除本地模型和专用 Provider，再移除工作流、MCP、工具编排和应用市场相关代码。每一组都清理注册入口、延迟导入、配置项和权限项，并验证 OpenAI 兼容模型与知识库模块可导入。

### 阶段三：前端裁剪

移除工作流、工具、市场和非核心媒体能力的页面、组件、路由和依赖。保留登录、工作区、模型配置、知识库、文档、问答和会话页面，以及人事模块入口。

### 阶段四：本地验收

- Python 依赖可安装，不拉取本地模型和已删除供应商 SDK。
- `python apps/manage.py check` 通过。
- 保留后端模块可导入，Django app 注册无失效引用。
- 前端依赖安装与 `npm run build` 通过。
- 前端构建产物不包含已删除工作流和模型 Provider 页面入口。

本轮不验收 Docker 构建、Docker Compose、生产守护进程、镜像大小或容器内知识库链路。

## 回滚与提交边界

按功能组分提交：模型与本地推理裁剪、后端编排裁剪、前端编排裁剪、非核心前端能力裁剪。每个提交均应能单独定位删除范围和验证结果。旧版 AgentKB 位于 `references/agentkb/`，只用于业务规则和测试迁移，不参与新版运行时。
