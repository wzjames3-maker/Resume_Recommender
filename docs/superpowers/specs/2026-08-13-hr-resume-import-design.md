# 简历上传与结构化解析设计

## 目标

在 `apps/hr` 中交付简历上传、规则型结构化解析、同工作区内容去重和候选人检索。解析不调用 LLM、不引入 Celery worker 依赖，采用同步执行并在简历记录上维护状态。本期不引入 PII 加密、AI 画像或 PDF 支持。

## 范围

### 范围内

- 候选人页支持批量上传简历（`docx`、`txt`）。
- 上传后同步解析，抽取姓名、邮箱、手机、当前城市、目标城市、学历、工作年限、技能、教育经历、工作经历。
- 解析结果回填到候选人档案；无法确定字段标空，不编造。
- 同工作区按文件内容 SHA-256 去重；重复上传返回既有记录并提示。
- 候选人列表检索扩展：姓名、技能、城市、工作年限、来源、状态。
- 简历文件本地落盘并记录元数据，工作区隔离。

### 不在范围内

- `doc`、`pdf`、`csv`、`json` 简历上传（严格拒收并提示）。
- LLM 画像、自然语言搜人、岗位匹配。
- PII 加密存储、候选人合并、版本化解析。
- 异步 Celery 解析与重试队列。

## 数据模型

### ResumeFile

- UUID 主键与 `workspace_id`。
- `file_name` 原始文件名，`extension` 白名单扩展名。
- `file_path` 本地落盘路径，`file_size` 字节数，`sha256` 内容哈希。
- `source_channel` 来源渠道，取值 `REFERRAL` / `JOB_SITE` / `HEADHUNTER` / `CAMPUS` / `OTHER`，默认 `OTHER`。
- `status` 解析状态，取值 `PENDING` / `SUCCESS` / `FAILED`，默认 `PENDING`。
- `error_message` 失败原因，可为空。
- `candidate` 可空外键，指向解析成功后创建的候选人。
- `user_id` 上传人，`create_time`、`update_time`。
- 数据库唯一约束：`(workspace_id, sha256)`，保证同工作区内容去重。

### 候选人字段扩展

一期 `Candidate` 已有字段足够承载解析结果，不新增列。解析结果只回填现有字段：`name`、`email`、`phone`、`current_city`、`target_city`、`highest_degree`、`years_experience`、`skills`、`source`、`note`（存教育/工作经历摘要文本）。

## 解析规则

### 文本提取

- `docx`：使用 `python-docx` 提取段落文本，忽略页眉页脚。
- `txt`：按 UTF-8 读取；解码失败回退 GBK，再失败标记解析失败。

### 字段抽取（正则 + 简单规则，不调用模型）

| 字段 | 规则 |
|---|---|
| email | 匹配 `[\w.+-]+@[\w-]+\.[\w.-]+`，取第一处。 |
| phone | 匹配中国大陆手机号 `1[3-9]\d{9}` 或带 `+86` 前缀；无则留空。 |
| name | 优先匹配「姓名[:：]」后的第一段；否则匹配首个中文姓名模式（2-4 个汉字），无法确定留空。 |
| current_city | 优先匹配「现居/现居住/所在城市[:：]」后的值；否则匹配「城市/地点[:：]」。 |
| target_city | 优先匹配「期望城市/意向城市/目标城市[:：]」后的值。 |
| highest_degree | 在学历关键词（博士/硕士/本科/大专/中专/高中）中取简历首个出现的最高级别；无法确定留空。 |
| years_experience | 匹配「N 年(工作经验|经验|工作经历)」或「工作 N 年」，取整数；无则留空。 |
| skills | 从「技能/专业技能/掌握技能[:：]」后的行按中文/英文逗号、顿号、分号分割并清洗。 |
| education / work | 从「教育经历」「工作经历」章节截取到下一章节标题，按行归并后写入 `note` 摘要（每段首行 + 时间范围）；本期不做结构化数组。 |

### 空值语义

字段无法确定一律空；不编造、不猜测。`skills` 无命中为空数组。

## API

统一前缀：`/admin/api/workspace/{workspace_id}/hr`。认证与权限沿用一期：成员可上传与解析，管理员可删除简历文件。

| 方法 | 路径 | 用途 | 最低权限 |
|---|---|---|---|
| POST | `/candidates/resumes` | 多文件上传并同步解析（`multipart/form-data`，字段 `files`、`source_channel`） | 成员 |
| GET | `/candidates/{candidate_id}/resumes` | 候选人简历列表 | 成员 |
| DELETE | `/resumes/{resume_id}` | 删除简历文件（保留候选人档案） | 工作区管理员 |

上传响应：`{"records": [{"resume_id", "file_name", "status", "sha256", "duplicate", "candidate_id"}]}`。重复文件 `duplicate=true` 且返回既有 `candidate_id`，不新建候选人。

跨工作区简历一律 404；未在白名单的扩展名或超 20 MB 的文件整体返回 400，不产生半批状态。

## 前端

- 候选人页新增「上传简历」入口，支持多选文件并选择来源渠道。
- 上传后展示每份文件结果：成功（跳转/刷新候选人）、重复（提示既有候选人）、失败（展示原因）。
- 检索区增加技能、工作年限、来源筛选项。
- 候选人详情显示已关联的简历文件列表。

## 测试

后端测试至少覆盖：

- `docx` 与 `txt` 简历成功解析并回填候选人字段。
- 同工作区重复文件返回 `duplicate=true`，不重复创建候选人。
- 不同工作区相同内容允许各自创建。
- 不支持扩展名、超大小文件整体拒绝且无残留记录。
- 跨工作区简历访问返回 404。
- 非管理员删除简历返回 403。

验收命令沿用一期：HR 测试、Django 检查、迁移漂移检查、前端类型检查与双构建。

## 取舍

- 同步解析优先于异步队列：本地无常驻 worker，解析量小，同步可形成最短可验收闭环；后续批次与重试再演进为 Celery。
- 规则解析优先于 LLM：本期保证字段抽取确定性和零模型成本；画像与智能搜人留到三期。
- 简历文件自管优先于复用 OSS `File` 表：避免 `source_type` 语义纠缠和 FileToken 鉴权体系耦合。
- 解析结果只回填一期字段，不新增结构化经历表；教育/工作经历以文本摘要存入 `note`，结构化经历表留到需要按经历检索时再引入。
