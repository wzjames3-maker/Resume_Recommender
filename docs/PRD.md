# MaxKB 人事招聘工作台 PRD

> 文档状态：产品基线，更新于 2026-08-16。本文同时描述已交付能力、真实候选人数据的上线门槛和后续路线；实现完成情况以第 9 节为准。
>
> 配套规格：业务对象的精确字段、闭合枚举与权限矩阵以 `docs/ATS-DESIGN-SPEC.md` 为准（该规格记录当前代码事实）；**目标 ATS 设计以 `docs/ATS-STATE-MACHINE-V2.md` 为准，传统 ATS 开源调研见 `docs/ATS-OPENSOURCE-REFERENCE.md`**；Agent + RAG 智能化设计见 `docs/PRD-AGENT-RAG.md`（D 阶段增补案，设计基线）。

## 1. 产品定位

人事招聘工作台是嵌入精简版 MaxKB v2 的多租户招聘模块，服务已经使用 MaxKB 工作区的中小招聘团队。它管理候选人、招聘需求、候选人在具体职位中的招聘流程，以及与招聘有关的简历和面试资料。

产品定位是轻量 ATS（Applicant Tracking System），不是独立的 HRIS/HCM：不建设组织树、员工档案、薪酬、合同、考勤或入职手续。Offer 被接受后，系统负责记录招聘结果并向既有 HRIS、OA 或人工交接流程输出所需信息。

招聘模块复用 MaxKB 的认证、工作区、模型管理和基础设施，但候选人及简历数据是独立业务数据，不得默认进入知识库、通用文档、Embedding 索引或模型上下文。

## 2. 目标与原则

### 2.1 产品目标

在一个工作区内，招聘团队能够完成以下闭环：

1. 录入、上传和检索候选人资料，并识别确定性重复档案。
2. 创建和维护可执行的招聘需求，将候选人以明确渠道和负责人关联到职位。
3. 推进筛选、面试、Offer 和招聘结果；保留可解释的操作和流程记录。
4. 在不越过租户、招聘职责和数据用途边界的前提下，使用规则搜索和 AI 辅助搜索、匹配。

### 2.2 产品原则

- **招聘需求优先：** `Job` 表示一项可执行招聘需求，不等同于企业统一职位目录或编制系统。
- **关系承载流程：** 候选人对不同职位的渠道、负责人、进度和结论属于候选人-职位关系，不写入候选人永久档案。
- **数据最小化：** 只收集完成招聘所需信息；自由文本不得记录身份证件、银行账户、健康、宗教、民族、婚育等不必要或敏感信息。
- **人工决策优先：** AI 搜索、解析和匹配只提供建议，不自动淘汰候选人、发放 Offer 或改变招聘状态。
- **先安全后扩展：** 未达到第 8 节的上线门槛前，仅可使用脱敏或测试数据，不得处理真实候选人 PII。

## 3. 用户、职责与访问控制

MaxKB 的用户和工作区仍是身份来源。招聘工作台在其上增加应用级访问资格，不重建独立认证。

| 招聘访问资格 | 能力边界 |
|---|---|
| 招聘查看者 | 查看获授权职位及候选人必要信息；联系方式默认脱敏；不得导出、下载附件、创建或变更流程。 |
| 招聘操作员 | 处理被分配职位或候选人：建档、上传简历、建立职位关联、维护筛选和面试信息。 |
| 招聘管理员 | 管理职位、负责人、成员授权、候选人归档/恢复、合并、受控导出和数据保留策略。 |

现有“工作区成员 / 工作区管理员”权限仅是历史实现，不能作为真实 PII 的最终权限模型。上线前必须将 HR 模块限制给被显式授予招聘访问资格的工作区成员；面试官在面试协作阶段仅能看到完成反馈必需的候选人与职位信息。

所有资源必须持久化 `workspace_id`。服务端从已认证主体的当前工作区派生租户范围，不信任 URL 参数；关联的 Candidate、Job、Assignment、Interview、ResumeFile 必须属于同一工作区。跨工作区资源对外统一按不存在处理，内部记录拒绝访问事件。

## 4. 核心业务对象与规则

### 4.1 Candidate（候选人档案）

候选人档案包含姓名、联系方式、城市、学历、工作年限、技能、人才库来源、通用备注和档案状态。手工建档至少要求姓名加一种联系方式；无联系方式的线索不得进入筛选流程。（**未实现**：当前代码仅强制姓名必填，联系方式可空；见 §8 对应门槛标注）

候选人状态：

| 状态 | 含义与规则 |
|---|---|
| `ACTIVE` | 可被搜索、关联到开放职位和继续处理。 |
| `ARCHIVED` | 不显示在默认运营列表，不能新建或恢复职位关联；恢复为 `ACTIVE` 后才可继续使用。 |
| 删除/匿名化 | 到期、撤回或经批准的删除请求进入异步清除流程。可保留去标识化的流程统计和受保护审计引用。 |

归档前不得存在进行中的职位关联。进行中状态包括 `PENDING_SCREEN`、`SCREEN_PASSED`、`INTERVIEWING` 和 `OFFER`。

### 4.2 Job（招聘需求）

招聘需求包含名称、部门文本、城市、职级、计划招聘人数、描述、技能要求、负责人和状态。计划招聘人数必须为正整数；编制审批和组织树不在本产品范围。

| 状态 | 含义与规则 |
|---|---|
| `DRAFT` | 草稿，仅负责人和管理员可编辑；不能建立职位关联。 |
| `OPEN` | 正在招聘；可以建立新的职位关联。 |
| `ON_HOLD` | 暂停招聘，例如预算冻结或 JD 调整；保留历史和在途记录，不能建立新关联。 |
| `CLOSED` | 招聘需求结束；必须记录原因：招满、取消、重复需求或其他。 |

关闭职位时，管理员必须逐项处理仍在进行中的关联，或进行有原因的批量收尾。不得留下无负责人、无结论的在途记录。

### 4.3 CandidateAssignment（职位申请/候选人职位关联）

> 本节表达产品意图；目标态的命令、守卫、事件与 API 以 `docs/ATS-STATE-MACHINE-V2.md` 为准，当前实现只作迁移基线。

该对象记录候选人进入某项招聘需求的事实和流程，字段包括候选人、职位、状态、关系类型、渠道、进入日期、当前负责人、筛选备注、创建人和更新时间。

关系类型至少包括候选人投递、主动寻访、内推和猎头推荐。渠道使用可统计枚举（内推/招聘网站/猎头/校园/其他）加"其他"详情，完整取值以 `ATS-DESIGN-SPEC.md` §2 枚举闭合表为准；候选人档案中的来源仅表示人才库首次来源，不能覆盖每次职位关联的渠道。终止原因为受控枚举（不适合/薪酬/无法联系/候选人退出/职位关闭/合并/其他），且与终态存在适配约束（如 REJECTED 不得搭配"职位关闭"），适配矩阵见该规格 §4.3。

| 状态 | 分类 | 规则 |
|---|---|---|
| `PENDING_SCREEN` | 进行中 | 等待初筛。 |
| `SCREEN_PASSED` | 进行中 | 已通过初筛，等待面试安排。 |
| `INTERVIEWING` | 进行中 | 存在或等待面试流程。 |
| `OFFER` | 进行中 | Offer 协商、审批、发送或等待接受。 |
| `HIRED` | 终态 | 招聘成功；候选人不得再新建职位关联。 |
| `REJECTED` | 终态 | 候选人不适合；必须记录受控拒绝原因。 |
| `WITHDRAWN` | 终态 | 候选人主动退出或无法继续联系；必须记录原因。 |
| `CLOSED` | 终态 | 因职位关闭、合并或其他流程原因终止；必须记录原因。 |

同一候选人与同一职位最多存在一条进行中的关联。`REJECTED`、`WITHDRAWN`、`CLOSED` 后再次参与该职位时，创建新关联并标记为重新投递/重新激活，旧记录保持不可覆盖的历史。`HIRED` 后不得新建职位关联；如候选人未来重新进入招聘，须先由外部 HRIS 或人工流程确认其不再是当前员工。误拒绝只能由招聘管理员恢复，并记录原因。

状态迁移遵守下表。除表内迁移外，服务端必须拒绝；管理员执行恢复或职位收尾时同样需要审计。

| 源状态 | 允许目标状态 | 附加规则 |
|---|---|---|
| `PENDING_SCREEN` | `SCREEN_PASSED`、`REJECTED`、`WITHDRAWN`、`CLOSED` | 进入终态必须填写受控原因。 |
| `SCREEN_PASSED` | `INTERVIEWING`、`REJECTED`、`WITHDRAWN`、`CLOSED` | 进入面试前可先创建或后补第一轮面试。 |
| `INTERVIEWING` | `OFFER`、`REJECTED`、`WITHDRAWN`、`CLOSED` | 面试反馈不自动改变关联状态。 |
| `OFFER` | `HIRED`、`REJECTED`、`WITHDRAWN`、`CLOSED` | 进入 `HIRED` 前须记录 Offer 接受结论。 |
| `REJECTED` | `PENDING_SCREEN` | 仅招聘管理员可恢复误拒绝，必须记录恢复原因。 |
| `WITHDRAWN`、`CLOSED`、`HIRED` | 无 | 不恢复原关联；按重新投递或员工离职后的新建规则处理。 |

### 4.4 ResumeFile（简历文件）

简历文件属于工作区，记录文件名、类型、大小、内容哈希、来源渠道、解析状态、关联候选人和上传人。当前已支持 `docx`、`txt`、异步规则解析、内容哈希去重、原件下载和提取文本查看。

已关联简历必须随候选人的删除或匿名化一并清理。允许未关联的待识别简历，但必须有独立访问控制、上传人和审计记录；上传后 30 个自然日仍未关联候选人的，由后台任务删除原文件、提取文本和解析结果，并记录清理事件。不得因候选人外键为空而绕开数据生命周期。上传、预览、下载和删除必须遵守候选人访问权限，并记录审计事件。后续格式扩展前必须定义文件类型/大小限制、恶意文件扫描、私有存储和短时授权访问。

### 4.5 Interview 与 Offer

`Interview` 记录职位关联、轮次、面试官、时间、结果和反馈。面试反馈是职位关联的业务资料，不得作为候选人通用备注。

`Offer` 是独立工件：版本（每关联版本唯一、服务端连续递增）、审批（产品规则为发送前置；代码待实现 R-D4）、金额与币种、发送、接受、拒绝、撤回和附件权限（VIEWER 不可下载）。Offer 状态与关联状态的联动规则（接受自动流转 HIRED 并触发幂等交接；拒绝/撤回后关联停留 OFFER 由人决定后续）以 `ATS-DESIGN-SPEC.md` §4.4/§5 为准。

## 5. 核心流程

### 5.1 建档、查重与关联职位

1. 招聘操作员确认候选人信息有合法来源并完成必要告知后，录入或上传候选人资料。
2. 系统按手机号和规范化邮箱做确定性查重，展示受权限控制的疑似重复结果；合并只允许招聘管理员执行。
3. 操作员从开放职位中选择招聘需求，填写关系类型、渠道和负责人。
4. 系统创建 `PENDING_SCREEN` 关联。归档候选人、暂停/关闭职位、已入职候选人和重复进行中关联均不得创建。

### 5.2 筛选、面试与职位收尾

1. 负责人从“待我处理”队列按职位、状态、城市、渠道和负责人筛选候选人；基础姓名、手机、邮箱定位不依赖 AI 或语义检索。（**待实现**：队列的精确契约——独立关联分页端点与筛选参数——见 `ATS-DESIGN-SPEC.md` §6；当前由候选人列表的负责人过滤与职位详情关联列表替代）
2. 状态变更必须满足状态机，并记录操作者、时间和终止原因。`REJECTED`、`WITHDRAWN`、`CLOSED` 不得以同一自由文本混用。
3. 初筛通过后安排面试并收集反馈。面试结果辅助招聘负责人推进或终止关联，不自动改变状态。
4. 关闭职位时，管理员确认每个进行中关联的去向，再完成关闭。招满、取消和暂停不得混为同一结论。

### 5.3 Offer 与入职交接

1. 通过面试的关联进入 `OFFER`，由具备权限的人员维护 Offer 工件和结论。
2. Offer 接受后关联进入 `HIRED`，系统生成面向目标 HRIS、OA 或人工流程的交接清单。
3. 本产品不创建员工档案、不办理合同或薪酬；交接失败应可重试且不能重复创建员工记录。

## 6. AI、知识库与集成边界

当前已交付自然语言搜人、职位描述技能抽取和基于技能/城市的确定性匹配。已交付的自然语言解析与结构化检索遵循 HR 显式授权（A3 已落地：HrAccess VIEWER/OPERATOR/ADMIN，VIEWER 联系方式脱敏）。匹配结果必须展示技能、城市等可理解依据。

候选人业务库是招聘事实的唯一来源。知识库、Embedding 和语义索引（已启用：简历语义索引）只能保存可重建的派生数据，并必须满足：

- 仅索引被明确允许的字段和文件；默认不发送候选人联系方式、备注或简历原文。
- 删除、归档、合并、权限变更后，在约定时限内清理或更新派生索引。
- 外部 LLM/Embedding 调用记录租户、模型、发送数据类别、用途和失败情况；模型供应商及数据地域须由工作区管理员选择或确认。
- AI 无法提供有效结果时回退到结构化筛选，不阻塞人工招聘流程。

## 7. 数据保护、审计与生命周期

以下条目是处理真实候选人信息的上线门槛，不得因后续功能延期而省略：

| 领域 | 最低要求 |
|---|---|
| 数据来源与告知 | 记录来源类型、收集日期、处理依据或告知确认、告知版本和联系偏好；不明来源不得录入真实 PII。 |
| 最小权限 | HR 模块显式授权；联系方式按职责脱敏；导出、附件下载和权限变更受管理员控制。 |
| 传输与存储 | 使用 TLS；数据库、备份和对象存储采用受控的静态加密；密钥不写入业务日志；手机号、邮箱、简历内容不得出现在普通日志、异常上报和监控标签中。 |
| 审计事件 | 记录候选人详情查看、创建、修改、归档/恢复/删除、职位开闭、关联与状态变更、简历上传/下载/删除、合并、导出、权限变更和越权拒绝。事件至少包含操作者、工作区、时间、对象、动作、结果和请求追踪标识（**未实现**：HrAuditLog 无 trace 字段，当前以 create_time + user_id + 动作组合追溯），普通成员不得改写或删除。 |
| 保留与删除 | 明确归档、恢复、到期删除、候选人撤回/更正请求、备份自然过期、租户注销和法律争议保留例外。历史统计优先去标识化保留。 |
| 导入导出 | 默认禁止通用批量导出；例外采用字段白名单、管理员授权和审计。候选人资料不得通过通用知识库或非 HR API 跨模块读取。 |

企业客户与平台的数据处理责任、数据所在地、分包处理、事件通知和数据返还/删除要求，应在部署或数据处理协议中明确。本 PRD 不替代法律意见。

## 8. 验收与非功能要求

每一阶段都必须有独立规格、测试和验收记录。针对试点规模（10,000 名候选人、500 个开放或历史职位、50 名并发工作台用户），至少满足：

- 候选人列表、基础字段检索和职位关联列表在常规查询下 P95 不超过 2 秒。
- 工作区隔离、职位/候选人状态限制、重复进行中关联和权限边界必须有自动化测试。
- 创建和编辑候选人的服务端必须校验姓名加至少一种联系方式（**未实现**：当前服务端仅校验姓名必填）；解析无法确定联系方式的简历只能停留在待识别状态，补全后才能创建候选人或关联职位。
- 所有真实 PII 访问与修改都能在审计中按对象、操作者和时间范围追溯。
- 简历上传、解析、下载、删除和异步失败状态有明确用户反馈；失败不产生半成品候选人或跨工作区文件访问。
- AI 搜索与匹配只能返回调用者有权查看的数据，并给出结果依据；无模型或模型失败时，基础检索可用。

生产上线前需要完成一次实际部署环境验证，包括对象存储权限、备份保护、任务队列、审计持久化和删除流程。仅通过本地单元测试或前端构建不能视为生产验收。
