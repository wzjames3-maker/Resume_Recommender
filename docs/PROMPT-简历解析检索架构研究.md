# 简历解析与检索架构研究提示词

> 用法：把下面整段（含【背景】与【问题清单】）交给 AI 研究工具，要求其对每个问题给出：根因分析、2~3 个候选方案、权衡、推荐方案、实施要点。

---

## 【背景】系统是什么

一个多租户人事招聘工作台（ATS），简历管理为核心。技术栈：
- 后端：Python 3.11 / Django 5.2 / DRF / PostgreSQL 16 + pgvector / Redis / Celery
- 前端：Vue 3 / Vite / Element Plus
- 模型：OpenAI 兼容接入（LLM: sensenova-6.8-flash-lite；Embedding: bge-large-zh-v1.5；Rerank: bge-reranker-v2-m3），通过 HrConfig 按工作区配置

### 简历处理管道（Celery 异步任务 parse_resume_task）
1. 提取原文：docx/txt → 纯代码提取（无 LLM，可靠）
2. 字段抽取：parse_resume_text（纯正则）→ 姓名/邮箱/手机/现居/目标城市/最高学历/工作年限/技能/备注
3. 语义索引：LLM 一次调用切片（split_resume_with_skills）→ 原文切成语义块(带 title) + skills → 每块 dense 向量入 pgvector → 检索用
4. 建候选人记录（含上面正则+LLM 产出的字段）

### 简历检索管道（search_resumes）
- hybrid = dense（块向量，语义召回）+ sparse（词法/BM25，关键词召回）→ RRF 融合 → Rerank 精排
- auto 模式会先用 LLM 解析查询里的技能/硬条件，走结构化预筛；显式 dense 模式跳过预筛

### 职位匹配（match_job_candidates，职位展开行「匹配候选人」）
- 结构化：job.skill_requirements 对 candidate.skills 精确/子串匹配
- 关键词召回：需求技能在简历正文(paragraph) ILike 命中即纳入
- 语义：dense 检索简历知识库合并；同分按导入时间排序

## 【问题清单】

### 问题 1：简历「技能」字段不可靠（最核心）
- 现象：正则只从「个人技能/特长」小节抽技能，简历无专门技能栏（技能散落在工作经历）时技能全空；有技能时抽出来是整句垃圾（如「2.根据市场营销计划」）。
- 影响：候选人列表技能列空、职位匹配一度匹配不到简历正文含技能的人（虽已用关键词召回+语义绕开，但字段仍脏）。
- 已尝试：
  - 让 LLM 从全文提技能（效果好，能抽出干净技能），但代价是每份简历多一次 LLM 调用，且与「LLM 只做切片总结」的原则冲突；
  - 已把技能提取并入切片那一次 LLM 调用（一次调用出 chunks+skills，省一次调用）。
- 待决策：技能到底要不要作为结构化字段？如果保留，用什么方式低成本、可靠地产出（LLM 总结时顺带 / 从块标题/关键词提取 / 干脆不存、需要时检索）？

### 问题 2：字段抽取的整体定位
- 现象：姓名/城市/学历/年限/技能正则都不够可靠（OCR 简历、自由排版简历经常抽错/抽空）。
- 一个候选思路：正则只保留「姓名+手机+邮箱」三个身份字段（可靠且产品必需），城市/学历/年限/技能降级为「尽力而为、缺省不惩罚」。
- 待决策：这样瘦身是否合理？产品前端哪些地方强依赖这些字段（列表展示、筛选、匹配）？瘦身后如何保证展示/筛选不退化？

### 问题 3：检索架构 ——「普通文本检索 + 稀疏向量 + 密集向量」如何分工
- 现状：dense=块向量（语义），sparse=块的词法/BM25（关键词），RRF 融合 + Rerank。
- 一个候选思路：
  - 普通检索直接匹配 docx 提取的原文文本（关键词命中保证召回）；
  - 稀疏向量负责「LLM 切片的总结」；
  - 密集向量负责「LLM 切片的原文」；
  - LLM 只负责切片+总结。
- 疑点/风险：
  - 稀疏向量若用 LLM 总结，总结是语义改写、可能不含原文关键词（如原文「微博微信营销」总结成「新媒体运营」），关键词召回会漏——稀疏到底应该用原文 token 还是总结？
  - 「直接在 docx 原文 LIKE」对全量简历性能差，是否应改为在块(保真原文)上做 BM25？
  - 总结字段（块级/简历级摘要）单独存，除了展示/审核，还能怎么用（稀疏增强、检索上下文）？
- 待决策：给出这四者（普通文本检索 / 稀疏=原文 or 总结 / 密集=块原文 / 总结字段）的最优分工与索引设计。

### 问题 4：LLM 职责边界与成本
- 现状：LLM 每次调用做切片（+ 顺带 skills）；检索侧 LLM 做查询理解（技能/硬条件解析）；Agent 用 LLM。
- 原则候选：LLM 只做「切片+总结」，字段/关键词/排序用便宜确定的方法。
- 待决策：这个原则是否成立？哪些环节值得用 LLM（切片边界、总结、查询理解、技能、评估），哪些必须用确定方法（手机/邮箱、关键词、BM25）？一次切片调用顺带产出哪些副产物最划算（summary / skills / title / 结构化字段）？

### 问题 5：前端与后端的字段契约脆弱（教训类，简述即可）
- 现象：后端返回字段名与前端读取不一致（如职位详情返回 applications、前端读 assignments）导致功能不可用；表单全局 CSS 覆盖导致布局塌陷；SPA 相对 base 导致子路由刷新白屏。均已修复。
- 待决策：如何从架构上避免这类问题（契约测试 / 类型生成 / 构建规范）？—— 本问题优先级低。

## 【研究要求】

对每个问题输出：
1. 根因（一句话）
2. 候选方案 2~3 个，每个标注：优缺点、成本（LLM 调用/存储/性能）、风险
3. 推荐方案 + 理由（要在成本、准确性、性能、可维护性之间权衡）
4. 实施要点（涉及哪些模块、改动多大、如何灰度/回退）

特别约束：
- LLM 成本敏感（flash-lite，每份简历调用次数要可控）
- 简历数据量大（569+ 份，持续增长），全量 LIKE/全量重算不可行
- 现有 pgvector + Celery + RAG 基础设施尽量复用，不要推翻重来
